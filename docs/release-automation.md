# 固定发布流程

新入口是 `.github/workflows/release.yml`，替代正式发版时同时运行 P4、P5、P6 和更新包四套流水线。历史流水线保留手动运行和 PR 验证入口；推送 `main` 不再自动启动 P5/P6 的重复发布构建。

发布目标为 `devilcoolyue/cursor-panel`。更新清单中的附件 URL 刻意保留旧仓库路径以兼容已安装的旧客户端，不能随展示链接一起替换；规则见[仓库更名与旧版兼容](repository-rename.md)。源码与验证附件使用 `cursor-panel-v版本号-*`，Python wheel 保留原包名。

## 发布一个版本

先把本次更新说明写到本地文件，再执行：

```bash
uv run --frozen python dev/release_cli.py prepare 0.0.5 --notes /绝对路径/本次更新说明.md
```

这一步只更新本项目版本、锁文件中的本项目条目、当前下载链接和版本归档。检查差异后正常提交并推送，随后启动一次发布：

```bash
uv run --frozen python dev/release_cli.py start --publish
```

命令要求干净工作区和已推送的相同提交，返回并保存一个 Actions 链接。CI 自行完成测试、构建、签名、上传和发布，关闭本地终端不会中断。省略 `--publish` 时只产出完整、已签名、已验证的发布附件，不创建 tag 或 Release。首次使用需将新流程文件合入默认分支；仓库继续使用已有的两个 `TAURI_SIGNING_PRIVATE_KEY` secrets。

查看进度不需要重新读取构建日志：

```bash
uv run --frozen python dev/release_cli.py status
uv run --frozen python dev/release_cli.py status --run 运行ID
```

输出只有任务状态、当前步骤和失败步骤。完整日志保留在 Actions 中，只有失败时才读取对应 job。

## 流水线的顺序

1. 校验确切提交、统一版本、版本说明、API 契约和 Linux 完整回归。
2. 三个平台先运行本平台完整回归与页面检查，成功后各冻结一次后台、编译一次 Tauri。服务端构建一次镜像和 wheel。
3. 对同一次构建的安装文件执行源码/冻结后台、系统适配、实际安装、首次/再次启动、异常退出清理及日志验证。签名复用这些产物；Windows 手动安装包与更新包来自同一个安装器。
4. 汇总四个目标，检查版本、源码、依赖锁、工作流来源、文件摘要、安装记录、更新签名及镜像配置，生成 19 个附件与总校验清单。
5. 只有验证通过且启动时带 `--publish`，才创建 tag 和草稿。按 Release ID 上传，核对远端摘要后公开，并检查 latest 接口与公开更新清单。

## 中断与失败

网络错误最多自动尝试三次；上传响应丢失时先查询远端摘要，已完整上传的文件直接复用。只清理当前草稿中同名的未完成上传条目，拒绝覆盖完整但内容不同的文件。创建草稿响应异常时先查找已有草稿，避免重复创建。

工作流失败后可以保留成功的平台产物，仅重跑失败 job：

```bash
uv run --frozen python dev/release_cli.py resume
```

测试断言失败不会被流水线自动重试或跳过。先看失败日志；代码需要修改时修复、提交并重新启动。因为 tag 在最终发布阶段才创建，构建失败不需要移动 tag。已有 tag 指向其他提交、同版本已发布但附件不同、重复草稿等冲突会停止，不自动覆盖历史版本。

发布 job 网络失败时，重跑只下载已构建附件并继续上传，客户端和服务端不重新编译。若发布已经成功但最后的网络核验失败，重跑只验证同一版本，不修改已公开附件。

## 对话与耗时

脚本输出取代逐条检查和临时拼装脚本，Actions 承担等待与网络重试。下一次可以直接说“用固定发布流程发布 vX.Y.Z”，或“在后台启动 vX.Y.Z 发布，给我任务链接”。后一种请求只需回报启动结果，后续按需查看 `status`。

这会减少需要模型处理的日志和操作轮数，不会消除编译、系统安装测试与上传本身的时间。若要求在同一会话等到完成，仍需等待 CI，但只跟踪一个任务即可。正式发布不降低签名、数据恢复和安装启动检查要求。
